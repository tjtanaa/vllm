# Qwen3.8-27B W4A16 + DFlash2 on AMD gfx1151 (Strix Halo)

Serving recipe for `dbirks/Qwen3.8-27B-W4A16-AutoRound` with a W4A16 DFlash2
draft model on an AMD Ryzen AI Max+ 395 / Radeon 8060S iGPU (gfx1151), using the
gfx1151-specific kernels in this tree.

Two configurations are given. **Use the agent one.** The benchmark one exists
only so the published numbers can be reproduced exactly.

| | script | context | prefix cache | KV |
| --- | --- | --- | --- | --- |
| local agent | `recipes/serve_gfx1151_qwen38_agent.sh` | 32768 | **on** | auto-sized |
| benchmark | `recipes/serve_gfx1151_qwen38_bench.sh` | 4096 | off | pinned 16 GiB |

## TL;DR

```bash
cd /app/qwen38opt/strixhalo
./recipes/serve_gfx1151_qwen38_agent.sh /tmp/vllm_agent.log &
tail -f /tmp/vllm_agent.log        # wait for "Application startup complete"
```

Startup is ~3.7 min the first time (model load, then `init engine` 174 s, then
CUDA-graph capture). With a warm `VLLM_CACHE_ROOT` later starts are faster.

Client:

```bash
curl -s http://127.0.0.1:8001/v1/completions -H 'Content-Type: application/json' -d '{
  "model": "dbirks/Qwen3.8-27B-W4A16-AutoRound",
  "prompt": "Explain what a receipt is in one sentence.",
  "max_tokens": 128, "temperature": 0
}'
```

## Prerequisites

* **Hardware**: gfx1151 APU, 40 CUs, 2 MiB L2, 256-bit LPDDR5X-8000. Measured on
  this box: 94.19 GiB unified memory, **242 GB/s** achievable read bandwidth
  (`benchmarks/kernels/probe_gfx1151_zero_copy.py`). The model is 14.8 GB of
  unavoidable weight traffic per decode step, so 61 ms/step is the hard floor.
* **Software**: `/opt/venv/bin/python3`, torch 2.12.0+rocm7.14.1. vLLM is
  installed **editable** against this tree (`pip show vllm` →
  `Location: /app/qwen38opt/strixhalo`), so `import vllm` picks up these kernels
  from any working directory — no `PYTHONPATH` needed.
* **Compiled extension**: `vllm/_rocm_C.abi3.so` must be built from this tree.
  The configuration below was verified against md5 `c5994ba3eb7d85f9…`. Rebuild:
  ```bash
  cd /app/qwen38opt/strixhalo
  PYTORCH_ROCM_ARCH=gfx1151 MAX_JOBS=8 /opt/venv/bin/python3 setup.py build
  # setup.py fails at its build_rust step (no Rust toolchain here); the
  # extension is already built by then, so just relink/deploy it:
  cd build/temp.linux-x86_64-cpython-312 && MAX_JOBS=8 ninja _rocm_C.abi3.so
  cp -f _rocm_C.abi3.so /app/qwen38opt/strixhalo/vllm/
  ```
* **Weights**: cached under `HF_HOME=/app/.cache/huggingface` (the scripts run
  with `HF_HUB_OFFLINE=1`). Target revision
  `1f05c441c4e64ae0549de44fa9ea5a6d43610314`, draft
  `syvai/Qwen3.8-27B-DFlash2-W4A16` revision
  `4d30ec736ffc6b8688dc2ae2b502d9b48bdec279`. Pin both: the launch-shape tables
  are tuned per projection shape.

## The agent command

```bash
HF_HOME=/app/.cache/huggingface \
VLLM_CACHE_ROOT=$HOME/.cache/vllm_gfx1151_qwen38 \
VLLM_GFX1151_W4_LDS_TILE=1 \
VLLM_GFX1151_W4_LOGITS=1 \
/opt/venv/bin/vllm serve dbirks/Qwen3.8-27B-W4A16-AutoRound \
  --revision 1f05c441c4e64ae0549de44fa9ea5a6d43610314 \
  --tokenizer-revision 1f05c441c4e64ae0549de44fa9ea5a6d43610314 \
  --served-model-name dbirks/Qwen3.8-27B-W4A16-AutoRound \
  --dtype bfloat16 --kv-cache-dtype bfloat16 \
  --max-model-len 32768 --max-num-seqs 2 --max-num-batched-tokens 4096 \
  --gpu-memory-utilization 0.85 \
  --cpu-offload-gb 0 \
  --language-model-only --generation-config vllm \
  --enable-prefix-caching \
  --compilation-config '{"inductor_compile_config":{"deterministic":true,"combo_kernels":false,"benchmark_combo_kernel":false}}' \
  --speculative-config '{"model":"syvai/Qwen3.8-27B-DFlash2-W4A16","revision":"4d30ec736ffc6b8688dc2ae2b502d9b48bdec279","method":"dflash","num_speculative_tokens":7}' \
  --host 127.0.0.1 --port 8001
```

## Context length: the trap that costs 40 % of your throughput

The tuned attention paths are gated on `1024 <= max_seq_len <= MAX_CONTEXT`, and
CUDA-graph capture runs with `max_seq_len` set to the **model maximum**. So if
`--max-model-len` exceeds the cap, capture takes the generic fallback and every
decode step replays it — silently, with no warning.

`MAX_CONTEXT` ships as **4096**, the value the delivered kernels were tuned and
tested at. `VLLM_GFX1151_QWEN_MAX_CONTEXT` raises it; the agent script sets it to
`$MAX_MODEL_LEN`. Measured at concurrency 1, `--max-model-len 32768`, identical
2-prompt probe:

| | cap 4096 (paths off) | cap 32768 (paths on) |
| --- | --- | --- |
| output throughput | 17.36 tok/s | **34.90 tok/s** |
| mean ITL | 140.51 ms | **100.31 ms** |
| accepted tokens/step | 2.57 | **3.91** |
| tuned paths in the log | none at M=8 | split-KV `D=256, M=8` + draft `D=128, M=8` |

Note the acceptance drop: the *draft* model's attention falls back too, so the
drafts get worse as well as slower. Both are recovered by the cap.

Raising it is a **no-op for a 4096-context run** (the reservation is
`min(max_model_len, cap) / 256` partitions and `max_seq_len` can never exceed
`max_model_len`), so the published benchmark configuration is unaffected.

Validated after raising the cap: needle retrieval from the first line of a
prompt is correct at **5,843 / 10,177 / 11,043 tokens** (a regime where the tuned
kernels had never run before), and
`tests/v1/attention/test_rocm_attention_backends_selection.py` covers the cap and
the scratch reservation it sizes.

## Flag reference

**Load-bearing — do not change without re-measuring:**

| flag / env | why |
| --- | --- |
| `--dtype bfloat16 --kv-cache-dtype bfloat16` | the W4A16 kernels implement exactly this contraction; fp8 KV is unvalidated here |
| `--cpu-offload-gb 0` | on an APU host memory *is* the same RAM the GPU already reads at 242 GB/s. Offloading only adds copies over a 82 GB/s path |
| `--language-model-only` | this checkpoint carries non-LM weights |
| `--generation-config vllm` | matches how the draft's sampling config was validated |
| `--speculative-config … method dflash, num_speculative_tokens 7` | width 7 is the tuned point; see "speculation width" below |
| `VLLM_GFX1151_W4_LDS_TILE=1` | K-tiled LDS W4A16 decode kernel. **Default off.** Worth +30 % at concurrency 1 (25.97 → 33.89 tok/s on its own) |
| `VLLM_GFX1151_W4_LOGITS=1` | derived int4 lm_head with exact top-K rerank. **Default off.** Worth +8 % (35.92 → 38.69) |

**On by default in this tree, pinned in the scripts for explicitness:**
`VLLM_GFX1151_QWEN_ATTENTION=1`, `VLLM_GFX1151_QWEN_GDN=1`,
`VLLM_GFX1151_W4_GROUP_MAJOR=1`,
`VLLM_GFX1151_QWEN_VERIFY_TILE=16,128,8` (`legacy` restores `16,64,4`),
`VLLM_GFX1151_QWEN_VERIFY_SPLITKV=1`,
`VLLM_GFX1151_W4_LOGITS_TOPK=256`.

**Tunable for your workload:**

| flag | benchmark value | agent value | notes |
| --- | --- | --- | --- |
| `--max-model-len` | 4096 | 32768 | the draft's own limit is overridden to match |
| `--max-num-seqs` | 8 | 2 | see the concurrency table below — this decides which W4A16 kernel you get |
| `--max-num-batched-tokens` | 2048 | 4096 | bounds the prefill chunk; raise it for long agent prompts to cut TTFT. 2048 is the measured value, 4096 is not benchmarked |
| prefix caching | **off** | **on** | off in the benchmark purely for run-to-run comparability. Measured on this model: decode is identical with it on and off (ITL 100.73 vs 100.31 ms, acceptance 3.91 both) and a repeated 9,111-token prompt goes **39.94 s -> 6.54 s TTFT (6.1x)** - exactly the agent pattern of resending a system prompt and tool schema every turn |
| `VLLM_GFX1151_QWEN_MAX_CONTEXT` | unset (4096) | `= $MAX_MODEL_LEN` | **must be >= `--max-model-len`** or every tuned attention path silently switches off. See below |
| KV sizing | `--kv-cache-memory-bytes 17179869184` | omitted | setting it makes vLLM *skip* memory profiling and ignore `--gpu-memory-utilization`. 16 GiB = **38,950 tokens** on this model (9.51x concurrency at 4096). For 32768 context let it auto-size, or pin ~32-40 GiB |
| `--gpu-memory-utilization` | 0.8 | 0.85 | of 94.19 GiB |
| `--seed 42` | set | omitted | only affects sampling; irrelevant at temperature 0 |

## Concurrency: the knob that changes which kernel runs

With a 7-token draft, **verified token batch = concurrency × 8**, and the W4A16
decode kernel is chosen by that batch:

| concurrency | token batch | W4A16 decode path | measured | median ITL |
| --- | --- | --- | --- | --- |
| 1 | 8 | K-tiled LDS HIP kernel, **190-228 GB/s** | **42.69 tok/s** | 125.4 ms |
| 2 | 16 | group-major Triton, ~110 GB/s | 49.07 tok/s | 219.8 ms |
| 4 | 32 | group-major Triton, ~100 GB/s | 68.18 tok/s | 253.7 ms |
| 8 | 64 | group-major Triton, ~50 GB/s | 65.79 tok/s | 521.6 ms |

So: **one conversation at a time gets by far the best per-token latency.**
Aggregate throughput keeps rising to concurrency 4 and falls at 8, but each
individual request is 2-4x slower there. For a single interactive agent set
`--max-num-seqs 1` or `2`. The int4 lm_head covers token batches up to 32, so
concurrency 4 still gets that part.

## What to expect

The published 42.69 tok/s at concurrency 1 is a **32-prompt sustained-load
aggregate**, and this package throttles ~22 % after ~4 minutes of continuous
work. Bursty interactive use stays cooler. Measured on the agent configuration
(32k context, prefix caching on) with a 2-prompt probe:

| | agent config | benchmark config |
| --- | --- | --- |
| output throughput | 34.69-34.90 tok/s | 34.85 tok/s |
| mean ITL | 100.31-100.95 ms | 100.50 ms |
| mean TTFT (1024-token prompt) | 3010-3020 ms | 2999 ms |
| acceptance length | 3.91 | 3.91 |

**The agent configuration is not slower than the benchmark one — it measured
faster.** Run as the full 32-prompt protocol, first workload on a fresh server:

| 32-prompt protocol, concurrency 1 | benchmark config | agent config |
| --- | --- | --- |
| output throughput | 42.69 tok/s | **44.96 tok/s** (+5.3 %) |
| acceptance length | 6.03 | 6.03 (identical) |
| acceptance rate | - | 71.86 % |
| mean ITL | 125.39 ms | **113.28 ms** |
| mean TPOT | - | 18.86 ms |
| mean TTFT | 3856 ms | **3485 ms** |

The TTFT gain is `--max-num-batched-tokens 4096` halving the prefill chunks; the
ITL gain is plausibly `--max-num-seqs 2` capturing smaller padded batch shapes,
though some of it may be throttle-state variation between runs.

**Do not compare a 2-prompt probe to the 32-prompt number.** Acceptance length is
a property of the prompt sample: the same server gives 3.91 on 2 prompts and 6.03
on 32 (`--dataset-name random` draws different content), and since
`tok/s = acceptance / TPOT` that alone moves 34.9 -> 45.0. The 2-prompt control
is still useful, because run against the *benchmark* configuration it gives the
same 34.85 tok/s / 100.50 ms / 3.91 — which is how the two configs were shown to
be equivalent. Rule of thumb: **~100-113 ms ITL, tok/s = acceptance / ITL**, so
~39 tok/s at acceptance 3.9 and ~53 tok/s at acceptance 6.0.

**Prefill is the weak spot for agent workloads.** Cold prefill runs at roughly
230-340 tok/s, so TTFT scales linearly with prompt length: ~3.0 s for 1024
tokens, ~28 s for 5,843, ~40 s for 9,111, ~55 s for 11,043. Prefix caching is
what makes this livable — the same 9,111-token prompt takes 6.54 s on a repeat
(6.1x). Keep your system prompt and tool schema **byte-identical across turns**
and put volatile content (the user's message) last, or you will not get the hit.

Other numbers to plan around: acceptance ~6.0-6.4 of 7 drafted tokens on the
benchmark corpus, ~33.9 GiB of the 80 GiB budget actually used at 32k context
with 25 GiB of KV (176-204k tokens), startup ~4.5 min.

## Verifying the fast paths engaged

These log at startup (during CUDA-graph capture) or on first use — grep the
server log. The benchmark configuration produces all of:

```
gfx1151 Qwen split-KV verification engaged: D=256, M=8              # change 8
gfx1151 Qwen Triton prefix engaged: D=256, M=8, tile=(16, 128, 8)     # change 4
gfx1151 Qwen Triton prefix engaged: D=128, M=8, tile=(16, 64, 8)      # draft
gfx1151 Qwen Triton prefix engaged: D=256, M=1024, tile=(64, 64, 8)   # change 5
gfx1151 Qwen fused HIP GDN core engaged: M=1                          # delivered GDN
```

The agent configuration (`--max-num-seqs 2`, 32k context) logs the split-KV
`D=256, M=8` line, the draft `D=128, M=8` line, the GDN line, and the
`M=1024 tile=(64, 64, 8)` prefill line once a long prompt arrives. Which exact
set appears depends on the shapes captured, but **`M=8` lines must be present**.

The two env-gated paths (`VLLM_GFX1151_W4_LDS_TILE`, `VLLM_GFX1151_W4_LOGITS`)
are silent — confirm the env vars are set in the server's environment, and use
median ITL as the observable: ~100 ms cold, ~125 ms under sustained load.
Without the LDS-tile kernel ITL is ~213 ms.

**If the `M=8` lines are missing from your log, `VLLM_GFX1151_QWEN_MAX_CONTEXT`
is below `--max-model-len`** and you are running the generic attention backend at
~60 % of the speed. That is the single easiest way to lose the optimization
silently.

## Things that look like they should help and measurably do not

Recorded so they are not re-litigated. Full evidence in
`benchmarks/results/c1_60tps/RUN_LOG.md`.

* **Wider speculation.** Width 15 moves the token batch to 16, where W4A16 costs
  117 ms/step instead of 66.7. Acceptance rises 6.03 → ~8.6, giving
  ~55 tok/s cold against today's ~58. Net negative.
* **A matrix-core (WMMA) W4A16 GEMM for batch >= 16.** Five independent designs
  — production Triton, WMMA with an LDS tile, WMMA with per-lane operands
  straight from global, VALU with per-thread NB=16, and VALU with 16 tokens split
  across two wave groups sharing one LDS weight tile — all land in
  **93-115 GB/s**. Global reads alone run at 229.8 GB/s (95 % of peak) and the
  matrix math costs only +34 us of a 443 us kernel; the ~200 us in between is
  delivering bf16 operands to the matrix core, and it costs the same through LDS
  or straight from global. Best achieved: 1.03x production (magic-number
  dequant), ceiling ~1.1-1.25x.
* **`--cpu-offload-gb`.** Zero-copy is total on this APU: device, pinned-host and
  registered-file-mmap memory all read at ~240 GB/s, and the CPU can dereference
  device pointers. Offloading adds copies over an 82 GB/s path for no gain.
* **Retuning the W4A16 launch-shape table, hoisting the bias correction out of
  the row loop, splitting a batch across concurrent workgroups, software
  pipelining the group staging, non-temporal weight loads, conflict-free LDS
  store mappings, split-K.** All measured; all flat or slower. The bias hoist is
  bit-identical and 2-13 % *slower* (register pressure — the kernel is
  memory-latency bound, not VALU bound).

What is genuinely left is the non-GEMM ~25 % of a decode step: prefill/TTFT
(~12 % of a 1K/1K request), host gaps ~5.5 ms, ~430 small norm/copy launches
~3.0 ms, attention 2.6 ms, GDN 2.0 ms.

## Accuracy

Greedy decoding, temperature 0, seed 42. The int4 lm_head masks logits outside
the approximate top-256 and reranks exactly, so its argmax is greedy-exact
(verified: the exact argmax always ranks <= 4 in the approximation). GSM8K smoke,
question IDs 0-99, five-shot, 8192-token budget: **97/100** with all changes
enabled, against references of 97/96/99. A full 1,319-question run has not been
done, so do not claim accuracy equivalence beyond the smoke set.
