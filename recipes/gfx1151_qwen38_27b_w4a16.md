# Qwen3.8-27B W4A16 + DFlash2 on AMD gfx1151 (Strix Halo)

Serving recipe for `dbirks/Qwen3.8-27B-W4A16-AutoRound` with a W4A16 DFlash2
draft model on an AMD Ryzen AI Max+ 395 / Radeon 8060S iGPU (gfx1151), using the
gfx1151-specific kernels in this tree.

Two configurations are given. **Use the agent one.** The benchmark one exists
only so the published numbers can be reproduced exactly.

| | script | context | prefix cache | KV |
| --- | --- | --- | --- | --- |
| local agent | `recipes/serve_gfx1151_qwen38_agent.sh` | 32768 | **on** | auto-sized |
| benchmark | `recipes/serve_gfx1151_qwen38_bench.sh` | 4096 | off | pinned 16 GiB |

## TL;DR

```bash
cd /app/qwen38opt/strixhalo
./recipes/serve_gfx1151_qwen38_agent.sh /tmp/vllm_agent.log &
tail -f /tmp/vllm_agent.log        # wait for "Application startup complete"
```

Startup is ~3.7 min the first time (model load, then `init engine` 174 s, then
CUDA-graph capture). With a warm `VLLM_CACHE_ROOT` later starts are faster.

Client:

```bash
  "model": "dbirks/Qwen3.8-27B-W4A16-AutoRound",
  "prompt": "Explain what a receipt is in one sentence.",
  "max_tokens": 128, "temperature": 0
}'
```

## Prerequisites

* **Hardware**: gfx1151 APU, 40 CUs, 2 MiB L2, 256-bit LPDDR5X-8000. Measured on
  this box: 94.19 GiB unified memory, **242 GB/s** achievable read bandwidth
  (`benchmarks/kernels/probe_gfx1151_zero_copy.py`). The model is 14.8 GB of
  unavoidable weight traffic per decode step, so 61 ms/step is the hard floor.
* **Software**: `/opt/venv/bin/python3`, torch 2.12.0+rocm7.14.1. vLLM is
  installed **editable** against this tree (`pip show vllm` →
  `Location: /app/qwen38opt/strixhalo`), so `import vllm` picks up these kernels
  from any working directory — no `PYTHONPATH` needed.
* **Compiled extension**: `vllm/_rocm_C.abi3.so` must be built from this tree.
  The configuration below was verified against md5 `c5994ba3eb7d85f9…`. Rebuild:
  ```bash

  PYTORCH_ROCM_ARCH=gfx1151 MAX_JOBS=8 /opt/venv/bin/python3 setup.py build
  # setup.py fails at its build_rust step (no Rust toolchain here); the
  # extension is already built by then, so just relink/deploy it:

  cp -f _rocm_C.abi3.so /app/qwen38opt/strixhalo/vllm/
  ```
* **Weights**: cached under `HF_HOME=/app/.cache/huggingface` (the scripts run
  with `HF_HUB_OFFLINE=1`). Target revision
  `1f05c441c4e64ae0549de44fa9ea5a6d43610314`, draft
  `syvai/Qwen3.8-27B-DFlash2-W4A16` revision
  `4d30ec736ffc6b8688dc2ae2b502d9b48bdec279`. Pin both: the launch-shape tables

## Context length: the trap that costs 40 % of your throughput

The tuned attention paths are gated on `1024 <= max_seq_len <= MAX_CONTEXT`, and
CUDA-graph capture runs with `max_seq_len` set to the **model maximum**. So if
`--max-model-len` exceeds the cap, capture takes the generic fallback and every
decode step replays it — silently, with no warning.

`MAX_CONTEXT` ships as **4096**, the value the delivered kernels were tuned and
tested at. `VLLM_GFX1151_QWEN_MAX_CONTEXT` raises it; the agent script sets it to
`$MAX_MODEL_LEN`. Measured at concurrency 1, `--max-model-len 32768`, identical
2-prompt probe:

| | cap 4096 (paths off) | cap 32768 (paths on) |
| --- | --- | --- |
| output throughput | 17.36 tok/s | **34.90 tok/s** |
| mean ITL | 140.51 ms | **100.31 ms** |
| accepted tokens/step | 2.57 | **3.91** |
| tuned paths in the log | none at M=8 | split-KV `D=256, M=8` + draft `D=128, M=8` |

Note the acceptance drop: the *draft* model's attention falls back too, so the
drafts get worse as well as slower. Both are recovered by the cap.

Raising it is a **no-op for a 4096-context run** (the reservation is
`min(max_model_len, cap) / 256` partitions and `max_seq_len` can never exceed
`max_model_len`), so the published benchmark configuration is unaffected.

Validated after raising the cap: needle retrieval from the first line of a
prompt is correct at **5,843 / 10,177 / 11,043 tokens** (a regime where the tuned
kernels had never run before), and
`tests/v1/attention/test_rocm_attention_backends_selection.py` covers the cap and
the scratch reservation it sizes.

## Flag reference

**Load-bearing — do not change without re-measuring:**

| flag / env | why |
| --- | --- |
| `--dtype bfloat16 --kv-cache-dtype bfloat16` | the W4A16 kernels implement exactly this contraction; fp8 KV is unvalidated here |
| `--cpu-offload-gb 0` | on an APU host memory *is* the same RAM the GPU already reads at 242 GB/s. Offloading only adds copies over a 82 GB/s path |
| `--language-model-only` | this checkpoint carries non-LM weights |
| `--generation-config vllm` | matches how the draft's sampling config was validated |
| `--speculative-config … method dflash, num_speculative_tokens 7` | width 7 is the tuned point; see "speculation width" below |
| `VLLM_GFX1151_W4_LDS_TILE=1` | K-tiled LDS W4A16 decode kernel. **Default off.** Worth +30 % at concurrency 1 (25.97 → 33.89 tok/s on its own) |
| `VLLM_GFX1151_W4_LOGITS=1` | derived int4 lm_head with exact top-K rerank. **Default off.** Worth +8 % (35.92 → 38.69) |

**On by default in this tree, pinned in the scripts for explicitness:**
`VLLM_GFX1151_QWEN_ATTENTION=1`, `VLLM_GFX1151_QWEN_GDN=1`,
`VLLM_GFX1151_W4_GROUP_MAJOR=1`,
`VLLM_GFX1151_QWEN_VERIFY_TILE=16,128,8` (`legacy` restores `16,64,4`),
`VLLM_GFX1151_QWEN_VERIFY_SPLITKV=1`,
`VLLM_GFX1151_W4_LOGITS_TOPK=256`.

**Tunable for your workload:**

| flag | benchmark value | agent value | notes |
| --- | --- | --- | --- |
| `--max-model-len` | 4096 | 32768 | the draft's own limit is overridden to match |
| `--max-num-seqs` | 8 | 2 | see the concurrency table below — this decides which W4A16 kernel you get |
| `--max-num-batched-tokens` | 2048 | 4096 | bounds the prefill chunk; raise it for long agent prompts to cut TTFT. 2048 is the measured value, 4096 is not benchmarked |
| prefix caching | **off** | **on** | off in the benchmark purely for run-to-run comparability. | `VLLM_GFX1151_QWEN_MAX_CONTEXT` | unset (4096) | `= $MAX_MODEL_LEN` | **must be >= `--max-model-len`** or every tuned attention path silently switches off. See below |
| KV sizing | `--kv-cache-memory-bytes 17179869184` | omitted | setting it makes vLLM *skip* memory profiling and ignore `--gpu-memory-utilization`. 16 GiB = **38,950 tokens** on this model (9.51x concurrency at 4096). For 32768 context let it auto-size, or pin ~32-40 GiB |

| `--seed 42` | set | omitted | only affects sampling; irrelevant at temperature 0 |

## Concurrency: the knob that changes which kernel runs

With a 7-token draft, **verified token batch = concurrency × 8**, and the W4A16
decode kernel is chosen by that batch:

| concurrency | token batch | W4A16 decode path | measured | median ITL |
| --- | --- | --- | --- | --- |
| 1 | 8 | K-tiled LDS HIP kernel, **190-228 GB/s** | **42.69 tok/s** | 125.4 ms |
| 2 | 16 | group-major Triton, ~110 GB/s | 49.07 tok/s | 219.8 ms |
| 4 | 32 | group-major Triton, ~100 GB/s | 68.18 tok/s | 253.7 ms |
| 8 | 64 | group-major Triton, ~50 GB/s | 65.79 tok/s | 521.6 ms |

So: **one conversation at a time gets by far the best per-token latency.**
Aggregate throughput keeps rising to concurrency 4 and falls at 8, but each
individual request is 2-4x slower there. For a single interactive agent set
`--max-num-seqs 1` or `2`. The int4 lm_head covers token batches up to 32, so
concurrency 4 still gets that part.

## Tool calling, thinking, and hooking it up to pi

### The tool-call parser must be `qwen3_xml`

This checkpoint's chat template emits an XML tool form, and the parser has to
match it or tool calls silently fail:

| `--tool-call-parser` | result |
| --- | --- |
| *(absent)* | HTTP 400: `"auto" tool choice requires --enable-auto-tool-choice and --tool-call-parser to be set` |
| `hermes` | HTTP 200 but **`tool_calls` is null** and the raw markup leaks into `content` |
| **`qwen3_xml`** | parsed: `name=calculator`, `arguments={"expr": "17*23"}`, `finish_reason=tool_calls` |

`qwen3_xml` maps to vLLM's `Qwen3EngineToolParser` (the same class as
`qwen3_coder`) and is what recipes.vllm.ai pairs with Qwen3.8-27B. The agent
script sets it by default; `TOOL_PARSER=""` disables tool serving.

### Two flags from that recipe do not apply here

* `VLLM_USE_RUST_FRONTEND=1` needs the `vllm-rs` binary. With
  `VLLM_RUST_FRONTEND_PATH=auto`, `envs.py` raises `FileNotFoundError` when
  `vllm/vllm-rs` is missing, and this tree was not built with setuptools-rust -
  so enabling it **breaks startup**. The script exposes `RUST_FRONTEND=1` for
  when you build it.
* `--mm-encoder-tp-mode data` is for multimodal encoder tensor parallelism; this
  server runs `--language-model-only` on a text model.

### Thinking is consumed and dropped by `--reasoning-parser qwen3`

> **SUPERSEDED 2026-10-04** — the agent script now defaults to
> `REASONING_PARSER=""` + the patched `qwen38_chat_template_thinking_off.jinja`
> (thinking OFF unless a request explicitly sends `enable_thinking=true`, and
> then visible inline in `content`). The stock-template + qwen3-parser combo
> below is kept for history; do not combine the patched template with the
> qwen3 parser: the parser starts in reasoning mode and drops the entire
> plain answer (verified: `391` → `content=None`, `reasoning_tokens=3`).
> pi-side pairing: `"reasoning": false` in models.json (pi then sends no
> `chat_template_kwargs`, and the patched default applies). Measured pi-pattern
> warm turns after the change: 18.5-26.4 tok/s at 8k-30k contexts (was ~7
> perceived with thinking on + parser dropping).

Measured on a short question: 113 completion tokens generated, ~60 surfaced, and
`reasoning_content` empty in **both** the non-streaming response and every
streaming delta. The parser strips the thinking block without re-emitting it, so
thinking costs tokens and latency invisibly. Turning it off
(`chat_template_kwargs: {"enable_thinking": false}`) produced a *longer*, fuller
answer (648 vs 233 chars) because no budget went to hidden reasoning.

If you want the reasoning visible, start the server with `REASONING_PARSER=""` -
then thinking arrives inline in `content` (verified). The agent script keeps
`qwen3` to match the upstream recipe.

## What to expect

The published 42.69 tok/s at concurrency 1 is a **32-prompt sustained-load
aggregate**, and this package throttles ~22 % after ~4 minutes of continuous
work. Bursty interactive use stays cooler. Measured on the agent configuration
(32k context, prefix caching on) with a 2-prompt probe:

| | agent config | benchmark config |
| --- | --- | --- |
| output throughput | 34.69-34.90 tok/s | 34.85 tok/s |
| mean ITL | 100.31-100.95 ms | 100.50 ms |
| mean TTFT (1024-token prompt) | 3010-3020 ms | 2999 ms |
| acceptance length | 3.91 | 3.91 |

**The agent configuration is not slower than the benchmark one — it measured
faster.** Run as the full 32-prompt protocol, first workload on a fresh server:

| 32-prompt protocol, concurrency 1 | benchmark config | agent config |
| --- | --- | --- |
| output throughput | 42.69 tok/s | **44.96 tok/s** (+5.3 %) |
| acceptance length | 6.03 | 6.03 (identical) |
| acceptance rate | - | 71.86 % |
| mean ITL | 125.39 ms | **113.28 ms** |
| mean TPOT | - | 18.86 ms |
| mean TTFT | 3856 ms | **3485 ms** |

The TTFT gain is `--max-num-batched-tokens 4096` halving the prefill chunks; the
ITL gain is plausibly `--max-num-seqs 2` capturing smaller padded batch shapes,
though some of it may be throttle-state variation between runs.

**Do not compare a 2-prompt probe to the 32-prompt number.** Acceptance length is
a property of the prompt sample: the same server gives 3.91 on 2 prompts and 6.03
on 32 (`--dataset-name random` draws different content), and since
`tok/s = acceptance / TPOT` that alone moves 34.9 -> 45.0. The 2-prompt control
is still useful, because run against the *benchmark* configuration it gives the
same 34.85 tok/s / 100.50 ms / 3.91 — which is how the two configs were shown to
be equivalent. Rule of thumb: **~100-113 ms ITL, tok/s = acceptance / ITL**, so
~39 tok/s at acceptance 3.9 and ~53 tok/s at acceptance 6.0.

**Prefill is the weak spot for agent workloads.** Cold prefill runs at roughly
230-340 tok/s, so TTFT scales linearly with prompt length: ~3.0 s for 1024
tokens, ~28 s for 5,843, ~40 s for 9,111, ~55 s for 11,043. Prefix caching is
what makes this livable — the same 9,111-token prompt takes 6.54 s on a repeat
(6.1x). Keep your system prompt and tool schema **byte-identical across turns**
and put volatile content (the user's message) last, or you will not get the hit.

Other numbers to plan around: acceptance ~6.0-6.4 of 7 drafted tokens on the
benchmark corpus, ~33.9 GiB of the 80 GiB budget actually used at 32k context
with 25 GiB of KV (176-204k tokens), startup ~4.5 min.

## Long-context acceptance collapse with prefix caching (found + fixed 2026-10-03)

Agent-style traffic (long contexts, prefix caching ON) used to collapse to
~6-7 tok/s: the DFlash2 draft is a 2048-token sliding-window model, and once
the scheduler evicted out-of-window draft blocks, the windowed attention kernel
still *loaded* them — masked-out `p=0` times Inf garbage in recycled/null
blocks is NaN (IEEE `0*Inf`), which poisoned the draft's accumulator rows and
every following step (constant proposals, acceptance 1.00). Cache OFF never
evicts, which is why the 1024-in/1024-out benchmark (seq <= 2048: no eviction
ever) never saw it.

Fixed in `vllm/v1/attention/ops/prefix_prefill.py`: the context loop now starts
at the trailing window (`SLIDING_WINDOW > 0 and not USE_SINKS` paths only;
target paths compile identically). Acceptance at 5.8k-10k contexts with caching
ON is back to 2.3-3.8, pi-like e2e 2.6 -> 6.5 tok/s (decode ~25 tok/s; the
residual e2e cost is cold prefill + hidden thinking tokens), and a fresh-server
A/B shows no short-context change (147.1 vs 146.3 ms/step).

Full audit trail, discriminators, and the two remaining e2e levers (cold
prefill; thinking tax — run pi with thinking **off** while
`--reasoning-parser qwen3` drops `reasoning_content`):
`benchmarks/results/dflash_window_nan_fix/RESULTS.md`.
Debug switches kept for future audits: `VLLM_DFLASH_DEBUG=1`,
`VLLM_DFLASH_KV_DBG=1` (default off, no prod cost).

## Prefill optimization stack (2026-10-03, /goal prefill 1..131072)

Profiled with `benchmarks/profile_prefill_stages.py` (per-stage torch.profiler
sweep; results in `benchmarks/results/prefill_decode_sweep/`). Prefill cost
model: `t ≈ a·L + b·L²/C` — GEMM linear in tokens (C = chunk size), attention
quadratic-in-depth re-reads of the cached context, once per chunk per layer.
Stage shares at 17k tokens: W4A16 GEMM ~74%, attention ~16%, GDN ~9%; at 103k
attention grows to ~50%.

Three changes, each measured:

1. **W4A16 GEMM M-binning** (`rdna_hybrid_w4a16.py`): the per-shape
   `_GFX1151_LARGE_M_OVERRIDES` (tuned at M=1024) lost 1.3-1.55x per GEMM at
   production chunk sizes. Now binned per shape: `<=1024` keeps the old
   configs, `>1024` uses configs swept at M=2250/3328/4160/7488
   (`benchmarks/kernels/sweep_gfx1151_w4a16_prefill.py`). Per-chunk GEMM time
   at M=4160: -28%. Correctness: rel_err 2.8e-3, 124 kernel tests pass.
   Server-level (warm): 3.3k-9k prefills **+25-33%** (239→306, 212→281 tok/s).
2. **Attention prefill tile** (`gfx1151_qwen_attn.py`): the target-prefill
   config `(64,64,8)` predates the split-KV/prefix rework and runs D=256
   attention at 6.4-7.3 TFLOPS. Swept with
   `benchmarks/kernels/sweep_gfx1151_attn_prefill_configs.py`:
   **`(128,64,8)` wins the whole gated range** — 1.36x at M=1024, 1.62-1.64x
   at M=2048-3328, **1.81x with deep cached context** (~11.6-12.0 TFLOPS).
3. **Chunk size 3328→7488** via `MAX_BATCHED_TOKENS=8320`: chunks are
   `align_down(budget-7, 832)` (mamba/GDN block-aligned split in the
   scheduler; the 4160 single-chunk cap seen earlier is the eagle-block-drop
   `last_cache_position` stop, not a budget limit). NOTE: total causal
   attention FLOPs are chunk-invariant (visible pairs telescope to L²/2); the
   gain is fewer per-chunk overheads (draft fwd/precompute/scheduler) plus
   better GEMM M. GEMM efficiency is flat per token at M=7488. Costs ~2 GiB
   of KV pool (activation profiling): 262k concurrency 1.42x → 1.29x.
   Budget 12544 was evaluated and rejected (seconds of overhead saved against
   another ~1.5 GiB of KV).
4. **Dequant→rocBLAS mm for prefill-sized M** (`rdna_hybrid_w4a16.py`,
   `VLLM_GFX1151_W4_DEQUANT_MM=1`, default off in envs.py, on in the agent
   script): the fused Triton W4A16 kernels dequantize inside the inner loop
   and plateau at ~15-16 TFLOPS; rocBLAS bf16 measures 19.9-26.4 TFLOPS on
   the production shapes. For **M >= 2048** the dispatch streams each layer's
   int4 weights through a cached bf16 workspace (<=912 MB for the five target
   shapes, ~1-2 ms per projection) and calls `torch.mm`. Dequant is bit-exact
   with the fused kernels' inner dequant (`bf16(code-8)*bf16(scale)`, ExLlama
   nibble shifts); only GEMM accumulation order differs (rel 1-2.4e-4 vs the
   fused path — the documented near-tie-flip class). Measured GEMM speedups:
   1.14-1.36x at M=3328, **1.20-1.67x at M=7488**. M<2048 stays fused
   (dequant traffic loses to the int4 read). KV pool cost 0.75 GiB
   (workspace; concurrency stays 1.29x at 262k).

## 262k context feasibility (measured 2026-10-03)

Both models natively cover 262,144 positions (target `text_config.
max_position_embeddings=262144`, no rope scaling; DFlash2 drafter
`max_position_embeddings=262144`, plain rope — and since the drafter is
sliding-window-2048, rope only matters through relative offsets inside the
window). The binding constraint is KV memory, and it fits:

```
MAX_MODEL_LEN=262144 MAX_SEQS=1 GPU_MEM_UTIL=0.92 ./recipes/serve_gfx1151_qwen38_agent.sh
  Available KV cache memory: 30.84 GiB
  GPU KV cache size: 372,328 tokens
  Maximum concurrency for 262,144 tokens per request: 1.42x
```

The hybrid architecture pays per-token KV for only the 16 full-attention
layers (~64 KiB/token bf16); the 48 GDN layers are constant-size per-request
state, so `MAX_SEQS=1` removes most of the fixed tax and bf16 KV fits with
42% headroom — no fp8/q4 KV kernel work needed (the gfx1151 backend only
supports auto/bfloat16 KV anyway).

Validated on this config: startup clean; split-KV `D=256, M=8` and draft
`D=128, M=8` tuned paths engage with `VLLM_GFX1151_QWEN_MAX_CONTEXT=262144`
(the agent script derives it from `MAX_MODEL_LEN`); short probe acc 8.0;
5.8k probe acc 2.6–3.7; **34.5k-token probe (past the old 32k cap) acc 2.52**,
no fallbacks, no crashes.

Costs to plan around at depth:

* Cold prefill ~200 tok/s measured at 34.5k — a full 262k prompt is a
  ~20-minute one-time ingestion. Prefix caching is mandatory for iterative
  use; keep stable prefixes byte-identical.
* Decode at full depth: attention KV reads add ~68 ms/step at 262k on top of
  the ~61 ms weight floor — expect ~12–16 tok/s (same physics as the
  llama.cpp 262k results: 11–24 tok/s realistic).
* `MAX_SEQS=1` — one request at a time (fine for a single pi agent).
* Not yet validated at the ceiling itself: needle retrieval at ~261k (the
  llama.cpp side proved 261,130/262,144; a vLLM-side run costs ~25 min of
  prefill per test) and GDN/split-KV behavior at full partition count
  (1024) under sustained load. Run once before relying on it.
* pi-side: `models.json contextWindow` (currently 32768) caps what pi sends.
  Raising it lets pi use the depth, but with it the compaction trigger
  (contextWindow − reserveTokens) moves out too — at this box's prefill
  speed, letting pi context grow past ~64k makes every turn minutes long.
  Recommended pattern: serve 262k for retrieval/document workloads via the
  API directly, and keep pi's working window modest.

## After syncing with upstream main: `rocm_segmented_attn`

The branch was merged with `origin/main` (1225 commits, 6 conflicts) on branch
`sync-main-segmented-attn`. That brought in `ROCM_SEGMENTED_ATTN`, a token-major
segmented Triton attention backend with an RDNA autotuner, gated on `on_gfx1x()`
so it does apply to gfx1151. It also brought `csrc/rocm/q_gemm_rdna3_wmma.cu`, a
production W4A16 **WMMA** kernel for M >= 16 - the exact matrix-core design that
could not be made to beat production above - but it is compiled only under
`#if defined(__HIPCC__) && defined(__gfx1100__)` and requires GPTQ zero points,
and `rdna3_w4a16.py` rejects anything but `on_gfx1100()`. `on_gfx1100()` is
False here, so neither applies to gfx1151 as shipped.

Measured A/B on the merged tree, identical recipe, only the backend differs
(`--attention-backend ROCM_SEGMENTED_ATTN` plus
`--kernel-config '{"enable_rocm_segmented_attn_autotune": true}'`):

| | gfx1151 (ours) | ROCM_SEGMENTED_ATTN |
| --- | --- | --- |
| cold prefill, 5421-token prompt | 20.35 s (266 tok/s) | **17.36 s (312 tok/s)** |
| warm prefill (prefix-cache hit) | 4.60 s | 4.56 s |
| decode, mean ITL (4-prompt probe) | **105.85 ms** | 127.35 ms |
| mean TTFT at 1024 tokens | **3038 ms** | 3729 ms |
| 512-token request incl. TTFT | 19.84 s | 19.55 s |
| startup time | ~4.5 min | **~13.5 min** (105 autotune workloads) |
| long-context needle retrieval | correct | correct |

**Verdict: keep the gfx1151 backend.** Segmented attention is genuinely better at
long prefill (+17 %) but 20 % worse on decode ITL and 23 % worse on short-prompt
TTFT, because our backend has hand-tuned split-KV verification and prefix tiles
for this model's exact M=8/M=1024 shapes while the segmented one is a general
autotuned kernel. Crossover: at 5421 prompt tokens it saves ~3.0 s of prefill but
costs ~21.5 ms per decode step, so it breaks even around **~512 output tokens**.
Use it only for ingest-heavy, short-output workloads (bulk document ingestion),
and expect the ~9 min one-time autotune - the tuner caches, so restarts should be
faster after the first.

Two merge notes worth knowing:

* `VLLM_ATTENTION_BACKEND` **is no longer read anywhere** in the merged tree.
  Backend selection moved to `--attention-backend` / `--attention-config`
  (`AttentionConfig.backend`, plus `backend_per_kind` for per-KV-cache-group
  overrides). Setting the old env var silently does nothing - the gfx1151 backend
  keeps running and no "token-major ROCm segmented" line appears.
* Our W4A16 kernel survived bit-exactly: 150/150 outputs identical to
  pre-merge references. Upstream's `zero_points` + `B_row_stride_bytes` changes to
  `skinny_gemms_int4.cu` did shift the *skinny* path's accumulation order at
  m=2/k=17408 only (max |delta| 0.25, both paths deterministic; m=3..64 still
  bit-identical), so the fork's cross-path bit-exactness test now asserts a 1%
  bound for that one case. m=2 cannot occur under speculative decoding, where the
  verified batch is concurrency x 8.

## Things that look like they should help and measurably do not

Recorded so they are not re-litigated. Full evidence in
`benchmarks/results/c1_60tps/RUN_LOG.md`.

* **Wider speculation.** Width 15 moves the token batch to 16, where W4A16 costs
  117 ms/step instead of 66.7. Acceptance rises 6.03 → ~8.6, giving
  ~55 tok/s cold against today's ~58. Net negative.
* **A matrix-core (WMMA) W4A16 GEMM for batch >= 16.** Five independent designs
  — production Triton, WMMA with an LDS tile, WMMA with per-lane operands
  straight from global, VALU with per-thread NB=16, and VALU with 16 tokens split
  across two wave groups sharing one LDS weight tile — all land in
  **93-115 GB/s**. Global reads alone run at 229.8 GB/s (95 % of peak) and the
  matrix math costs only +34 us of a 443 us kernel; the ~200 us in between is
  delivering bf16 operands to the matrix core, and it costs the same through LDS
  or straight from global. Best achieved: 1.03x production (magic-number
  dequant), ceiling ~1.1-1.25x.
* **`--cpu-offload-gb`.** Zero-copy is total on this APU: device, pinned-host and
  registered-file-mmap memory all read at ~240 GB/s, and the CPU can dereference
  device pointers. Offloading adds copies over an 82 GB/s path for no gain.
* **Retuning the W4A16 launch-shape table, hoisting the bias correction out of
  the row loop, splitting a batch across concurrent workgroups, software
  pipelining the group staging, non-temporal weight loads, conflict-free LDS
  store mappings, split-K.** All measured; all flat or slower. The bias hoist is
  bit-identical and 2-13 % *slower* (register pressure — the kernel is
  memory-latency bound, not VALU bound).

What is genuinely left is the non-GEMM ~25 % of a decode step: prefill/TTFT
(~12 % of a 1K/1K request), host gaps ~5.5 ms, ~430 small norm/copy launches
~3.0 ms, attention 2.6 ms, GDN 2.0 ms.

## Persistent KV — NVMe-direct tier + retention checkpoints (2026-07-27, RECOMMENDED)

Full analysis: `benchmarks/results/nvme_direct_phase2/RESULTS.md` (Phase 2);
`benchmarks/results/native_offload_phase1/STATUS.md` (Phase 1, CPU+fs tiering).

- `NvmeDirectOffloadingSpec` (`vllm/v1/kv_offload/nvme_direct/`) writes KV
  chunks **straight between the GPU pool (host-visible unified memory) and
  NVMe files** via thread-pooled writev/preadv — no CPU staging region, no
  padding (13% denser), and a **synchronous adopt-on-lookup** so a restarted
  server serves hits on its first request.
- Spec decode changes the game: EAGLE trailing-drop moves the resume boundary
  off the last GDN checkpoint, so with the default
  `prefix_cache_retention_interval=0` (latest-boundary-only) restarts always
  recomputed. **`--prefix-cache-retention-interval 832`** (must be a multiple
  of tokens_per_chunk, here 832) stores dense GDN checkpoints and fixes it.

```bash
OFFLOAD_ROOT=/app/kvstore_direct MAX_MODEL_LEN=262144 MAX_SEQS=1 \
GPU_MEM_UTIL=0.92 MAX_BATCHED_TOKENS=8320 \
recipes/serve_gfx1151_qwen38_agent_directnvme.sh /var/log/vllm.log \
    --prefix-cache-retention-interval 832
```

| 32.7k doc, production geometry | no connector | CPU+fs tier | NVMe-direct + retention |
|---|---|---|---|
| cold prefill | ~224 tok/s | 102–107 tok/s | 103–104 tok/s |
| warm restore | — (recompute) | 18.8 s | 18.8 s |
| first request after restart | recompute | 336.5 s recompute | **19.3 s restore** |
| storage per doc | — | 2.7 GB (sparse) | 4.24 GB (dense GDN) |
| staging RAM | 0 | 1 GiB | **0** |

Remaining known tax: cold prefill ~103 vs ~224 tok/s without the connector —
per-chunk store preparation on the engine critical path (identical on both
paths); next lever is batching/async `prepare_store`.

Legacy alternative (Phase 1): `TieringOffloadingSpec` (CPU 1 GiB staging + fs
tier + `FsAsyncLookupManager` patch) via
`recipes/serve_gfx1151_qwen38_agent.sh` with `OFFLOAD_ROOT`/`OFFLOAD_CPU_GB` —
same warm-restore speed, but restart-first-request needs the retention flag
AND still pays the async-lookup one-step lag; kept for reference.
